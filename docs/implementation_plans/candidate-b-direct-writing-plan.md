## 1. 目标与比较问题

在保留基线 A 行为的前提下，增加候选 B。用户可以手动选择流程，默认继续执行 A。

- A：输入 → 标准化 → 大纲规划 → 正文撰写 → 格式整理 → 结构校验 → 保存。
- B：输入 → 标准化 → 直接撰写完整正文 → 格式整理 → 结构校验 → 保存。

主比较问题：面对同一个备课需求，分步规划写作与直接写作两套完整流程，在正文与成品、耗时、可获得的 token 用量和失败情况上有何差异。

每条流程必须独立从输入执行到保存。复用公共代码，不复用另一条流程生成的大纲、正文或最终稿。B 没有独立大纲步骤，不执行、读取或伪造该步骤。

结果解释限于完整流程差异。取消独立大纲步骤还会改变提示词、上下文和调用次数，不能据此把全部差异归因于“大纲本身”；直接写作也不等于模型内部没有规划。

## 4. 必须遵守的设计与兼容约束

### 4.1 流程入口与身份

- 为 `run_lesson_pipeline` 增加关键字参数 `pipeline`，默认值为 `outline_then_write`；B 使用 `direct_write`。
- CLI 增加对应的 `--pipeline` 参数，允许这两个值；原有省略参数的命令继续运行 A。
- 保留现有 `run_lesson_pipeline` 返回类型、已有参数及其含义；保留 A 的 `build_phase1_graph` 入口。
- 流程标识是稳定名称，流程版本单独记录。不要将 A/B 字母、Phase 1/Phase 2 阶段名或包版本混作流程身份。
- 未知流程属于入口配置错误，应在模型调用和建立运行目录前明确拒绝，不静默回退，也不伪装成 Normalize 的输入内容错误。
- 提供可选的 `comparison_id` 关键字参数和 CLI `--comparison-id`，只用于关联一组配对运行，默认 `null`。不自动执行另一条流程。
- 流程选择与比较标识放在运行参数和元信息中，不写入 `LessonTask`，避免改变教案任务 Schema。
- 简单、显式的流程分派即可；不为两个流程建立通用插件体系。

### 4.2 DirectWriter 的职责

新增 `DirectWriterAgent` 和独立提示词 `direct_writer_v1.txt`。

- 输入为本次运行标准化后的 `LessonTask` 和可选资料，输出为 `ModelResult[LessonDraft]`。
- 输入 payload 不包含 `outline`，不接收其他运行生成的中间结果。
- 一次结构化生成完成标题、概述、教学目标、重难点、详细阶段、作业和备注。
- 明确要求遵循学科、年级、主题、课时、语言和用户要求，并提供教师活动、学生活动及形成性评价。
- 不生成教学质量分数，不调用大纲 Agent，不以内部额外模型调用模拟“大纲后写作”。
- 沿用现有 Provider 接口；DirectWriter 初始 temperature 为 `0.2`，与当前 Writer 一致。
- 独立维护提示词版本；保留 A 的 `outline_planner_v1.txt`、`writer_v1.txt` 和共同的 `formatter_v1.txt` 内容。

不要把现有 Writer 的 `outline` 改成可选参数后塞入两套职责，以免 A 的契约和提示词随 B 漂移。

### 4.3 Graph 与公共后处理

B 的实际节点顺序固定为：

```text
normalize_input -> direct_writer -> formatter -> schema_validate -> save
```

- 新增独立的 B Graph 构建函数，例如 `build_direct_write_graph`，接受与 A 一致的 Provider、Retriever、RunContext、aliases 等依赖。
- A 保持原六节点顺序，保留现有 `PHASE1_NODE_ORDER` 的 A 语义；B 使用自己的节点顺序定义。
- 小范围提取 Formatter 节点工厂，让 A、B 共用同一份执行、artifact、trace 和异常处理逻辑。
- Normalize、Validator、Save 继续共用，不为 B 复制一套规则。
- 两条流程的 Formatter 使用同一 `FormatterAgent` 实现、提示词及 `0.0` temperature，节点与运行上下文各自创建；保持输入任务元数据只读。
- 两条流程分别初始化 State、RunContext、run_id 和运行目录。不得复用另一次运行的可变 State、trace 或消耗过的 Mock 响应队列。
- 公共代码抽取应保持 A 的业务行为；不顺带改写整个节点执行框架。

### 4.4 Schema、State 与输出契约

- B 继续输出现有 `LessonDraft`，经共同 Formatter 形成现有 `LessonPlan`。
- 不降低详细阶段字段要求，不放宽额外字段规则，也不另建一个更宽松的 B Schema。
- B 的 State 中没有 `outline`；不写空对象或虚假占位数据。其 `draft`、`formatted_plan`、`validation` 等字段保持既有含义。
- 继续逐字段验证最终 `LessonPlan.task` 与标准化任务一致。
- `LessonDraft` 是未来 C、D 接入共同后处理的边界；本次无需实现它们，也无需增加覆盖所有未来流程的联合 State。
- 不加入没有真实生产者和消费者的评分、修订或多轮字段。

### 4.5 文件与失败语义

A 的既有文件名和主体结构保持兼容：

```text
input.json
run_meta.json
01_normalized.json
02_outline_planner.json
03_writer.json
04_formatter.json
05_schema_validation.json
state.json
trace.jsonl
final.json
```

B 的成功运行包含：

```text
input.json
run_meta.json
01_normalized.json
03_direct_writer.json
04_formatter.json
05_schema_validation.json
state.json
trace.jsonl
final.json
```

- B 省略大纲文件，编号允许不连续；文件前缀表示兼容命名，不作为实际执行顺序的依据。
- 实际顺序读取 trace；正文位置根据流程标识或 artifact 映射定位。不得让通用读取逻辑永远假设存在大纲或 `03_writer.json`。
- 记录增强优先扩展现有 `run_meta.json` 和 trace 字段，保留以上成功产物集合；固定小规模资料可内嵌元信息，不要求本次新增资料文件体系。
- 缺字段、非对象 JSON 等已解析输入错误，仍进入 Normalize，保留原始输入及失败 State，并且不调用模型。
- DirectWriter 或 Formatter 异常后停止后续业务处理，保存能够保存的失败 State 和 trace。
- 结构校验返回无效时，Save 只保存失败记录，不生成正式结果。
- 保存 final、state、trace 时出现可恢复异常，移除本次残留或损坏的 `final.json`，返回失败。
- 新增必要元信息写入也不得导致“运行失败却留下正式 final”或“记录失败却返回完成”。统一完成路径需覆盖成功、节点异常和保存异常，不能只在成功返回前补写。
- 输入文件读取、JSON 文本语法、Provider 初始化等 Graph 外入口错误，沿用现有边界；不承诺本次建立完整的入口失败档案。
- 持续无法写入或删除文件、半截 trace、强制终止等情况，不扩张为本次的事务或恢复保证。

## 5. 比较所需的最小运行记录

以下为规划时确定的记录要求。具体实现和执行证据见验收记录；字段可在现有结构中合理分组，但含义必须稳定，并在 `docs/dataset_schema.md` 说明。

### 5.1 身份、版本与输入关联

- `metadata_schema_version`：元信息格式版本，区别于业务流程版本。
- `pipeline_id`、`pipeline_version`：实际所选流程及行为版本。提示词、参数或业务路径的变化需可追溯，不沿用旧版本冒充同一条件。
- `comparison_id`：由调用方指定的配对标识；独立运行允许为空。
- `run_id`：每次执行独立生成；即便任务与流程相同，也不得覆盖此前运行。
- `input_hash`：对已解析原始 JSON 值做稳定序列化后的 SHA-256。明确键排序、UTF-8 编码及序列化规则；不是输入文件原始字节的哈希，也不是教学语义相等的证明。
- 标准化任务哈希：Normalize 成功后记录；失败时为未知。与原始输入哈希区分，并继续保存完整输入和标准化结果。
- `code_version`、`git_commit`、工作区修改状态：记录实际执行版本。Git 不可用或无法确定时保留 `null` 并说明原因，不编造提交号。
- 各实际参与 Agent 的提示词版本和内容 SHA-256；哈希从运行使用的模板文本派生。Provider 的结构化适配仍通过代码版本追溯。

`task_id` 不能单独证明两次输入一致。不同要求可能沿用同一编号；同一原始输入也可能因 aliases 不同而得到不同标准化结果，因此仍需保留实际 aliases 并核对标准化任务。

行为基线提交号与实际执行提交号必须区分：B 加入后的 A 可以保持基线行为，但其 `git_commit` 应记录新增 B 后的真实代码版本，不能继续硬填 `b9dcded`。

### 5.2 模型、配置与耗时

- 继续从实际 Provider 和 Agent 对象取得 Provider 名称、模型 ID、base URL、temperature、配置来源；不根据未加载的 YAML 推测。
- 保留实际的 normalization aliases、dotenv/config 加载状态。不得把密钥或整个环境变量快照写入产物。
- B 的元信息中只列本次配置参与的 DirectWriter 与 Formatter，不列不存在的大纲 Agent；实际执行到哪些节点以 trace 为准。
- 模型 ID 按可获取的信息如实记录；现有适配器主要记录配置的 ID，不应声称已核实服务端别名解析后的精确模型版本。
- 在运行记录中增加端到端耗时，使用单调时钟，并固定、说明计时起止位置。该计时覆盖运行初始化、Graph 执行及结束处理的既定范围，不用节点耗时之和冒充完整耗时。
- 保留既有节点耗时；说明其包含节点内检索、模型调用及部分落盘开销，不将其直接解释成纯模型推理时间。
- 保留可取得的 token usage。未知用量仍为 `null`；任何汇总都要标明缺失，不能把失败或缺失用量填成零后宣称得到完整总量。
- 应说明 Provider 是否显式设置超时、重试、输出上限等。未显式设置时注明使用客户端默认；正式比较时固定客户端版本与条件，不在本次臆造默认参数值。

代码版本信息获取失败本身不应使正常教案生成失败；必要运行记录的实际落盘错误则仍受第 4.5 节失败语义约束。

### 5.3 实际提供的资料

- 保留 `KnowledgeRetriever` 接口，本次不接入真实检索。
- 默认比较使用两条流程共同的空资料条件；需要非空资料时，使用相同的固定资料快照，并明确记录该条件。
- 在现有运行元信息中按调用节点保存实际查询、实际返回并交给 Agent 的资料内容、可获得的来源/版本，以及快照哈希。
- 空资料 `[]` 与该节点未执行、检索失败或资料未知要能区分。不要将未调用节点记录成已成功取得空资料。
- A 保留现有两次检索及其查询；B 直接写作使用与 A Writer 相同的“撰写教学活动”查询规则，获取一次资料。不为统一调用次数而修改 A。
- 非空资料的记录应在模型调用前建立，避免模型失败后完全丢失其资料条件；不得只依赖最终 `LessonPlan.sources` 反推实际使用过的资料。

未来真实检索即使访问同一资料库，也可能因查询、索引版本或时间不同返回不同内容。届时需重新定义控制条件，不能将“同一资料库”直接视为“同一输入资料”。

### 5.4 旧记录兼容

以下约束适用于本次涉及的读取和验收逻辑，不要求新增独立历史记录读取器。

- 新字段采用增量扩展，保留既有字段的含义。
- 新的读取或验收逻辑允许旧元信息缺少流程、哈希和格式版本等字段，显示为历史缺失或未知，不因新增字段强制迁移旧目录。
- 不无条件把缺少 `pipeline_id` 的所有历史记录判定为 A；需要基于其来源、节点和产物判断，不能补造证据。
- 未来若扩充产物文件或更改记录布局，应显式升级格式并更新验收，不通过删除原有断言掩盖兼容性变化。

## 6. 给未来保留的边界

本次保留三处实际有用的接口：流程入口、`LessonDraft` 到公共后处理的边界、现有 Retriever/Provider 依赖接口。运行身份和记录版本为以后增加候选提供区分能力，不代表要立即建立通用框架。

候选 C 将分阶段结果整合为 `LessonDraft` 后接入；候选 D 在需求分析后生成 `LessonDraft` 再接入。两者未来各自有独立流程名、版本和运行记录，不借用 A 或 B 的身份。

反馈修订目前存在明确的契约问题：[Evaluator](../../src/lesson_agents/agents/evaluator.py)和 [Critique](../../src/lesson_agents/agents/critique.py)接收 `LessonPlan`，而上位方案的反馈节点位于 Formatter 前，此处只有 `LessonDraft`。进入修订研究时必须先决定评价正文还是最终稿，再调整接口和流程位置。

本次不为迎合占位接口而额外调用 Formatter，也不直接采用其中的占位评分维度或阈值。修订的父版本、反馈来源、修改前后稿、revision id 和轮次，留待修订阶段定义。

现有 trace 的 `iteration` 固定为 `0`，本次仍保持一次生成；这不等于已支持多轮。未来重复执行同一节点时还需解决产物不覆盖和执行实例标识，不能仅把 `iteration` 改成自增。

## 7. 会影响比较有效性的条件

### 7.1 固定行为基线，独立完整执行

- 本次 A 的行为基线固定在文首提交。开始实施时重新核对工作区和最新版本；若已变化，检查变化对本计划的影响并更新事实，不能默默更换比较基线。
- 同一比较批次尽量在同一个已记录的实现版本与依赖环境下运行 A、B，A 保持已验收行为；公共记录增强同时适用于两者。
- 公共抽取不得改变 A 的模型输入、提示词、参数、检索逻辑和校验标准。必要行为修复应单独说明，重新建立相应基线再比较。
- 每条流程独立标准化并生成自己的中间结果；可以共享固定外部资料，不能共享模型生成的大纲或正文。

### 7.2 Formatter 是共同的模型环节

- Formatter 会把 `LessonDraft` 转成 `LessonPlan`，其中还包括整体 `assessment`、`sources` 等字段；它不是纯文本排版程序。
- 必须保留整理前正文和整理后结果。后续评价应能检查信息丢失、补写和变化，不能把最终差异全部归因于 DirectWriter。
- 共同 Formatter 的提示词、模型和参数保持一致；不为 B 增加隐藏的内容修复或额外重试。

### 7.3 用量、时延与失败的统计边界

- A 正常成功路径为三次 Agent 调用，B 为两次。节点数不等于服务端实际请求次数，SDK 内部重试等因素可能改变请求数量。
- B 单次输出可能更长，不能仅凭少一次调用判定更快或更省 token。
- 比较时统一模型、参数、输入、资料条件、Schema、公共后处理和校验规则，记录环境与依赖版本。
- 保留全部失败尝试及失败节点，不只统计成功成品；再次执行应生成新的 run_id，并保留与同组比较的关联。
- 当前 CLI 主要打印结果，没有按失败状态设置非零退出码。后续脚本应检查运行 `status`、`validation.valid` 和产物，而不能只看进程退出码。本次不顺带变更 CLI 退出码契约。
- 本计划不实现自动费用计算或批跑平台；缺失的失败请求用量、未知价格等不能推算成确定费用。

### 7.4 工程通过不等于教学质量通过

- 当前 Validator 检查结构、必需集合、详细阶段字段、非负时长以及任务元数据一致性。
- 它不证明知识正确、学科适切、用户要求在正文中充分落实，或所有阶段时长总和符合课时。元数据未改写也不等于内容满足要求。
- Mock 响应只能验证结构和工程路径。A、B 的 Mock 内容即便相同，也不能用来推断真实生成质量相同。
- 正式教学评价由团队与老师确定；不采用仓库占位评分或把模型自评分当作结论。
- 后续真实比较使用多个需求、适量重复运行，保留失败样本；记录运行次序，并尽量交错 A、B 以减小服务时段差异。评价成品时尽可能隐藏流程标签，人工评价另存，不覆盖原稿。
- 输入集合、提示词和模型条件改变后，应区分比较批次；不凭一次结果判断优劣。
- 同一大纲或同一初稿的局部对照属于后续解释性实验，单独标记，不混入本次完整流程结果。

## 9. 工程验收标准

### 9.1 基线兼容

- 不传流程参数与显式选择 A 的行为一致，旧 Python 调用和 CLI 命令仍有效。
- A 的原有测试继续通过，包括节点顺序、模型 payload、提示词/参数、产物文件名、任务一致性和失败保存。
- A 的提示词内容、六节点路径、三次结构化调用及原 Schema/Validator 规则保持不变。
- 元信息增量字段不删除旧字段，不用修改或删除业务断言掩盖回归。

### 9.2 B 的完整路径与独立性

- B 正常执行五个节点，模型调用 Schema 顺序恰为 `LessonDraft`、`LessonPlan`。
- DirectWriter payload 包含本次任务及资料，不包含大纲；Formatter 消费本次 DirectWriter 的 draft。
- State、trace、元信息和文件中没有伪造的大纲执行或产物；元信息中的 Agent 与所选流程一致。
- 最终稿符合现有 `LessonPlan` 和 Validator，任务全部字段与标准化结果一致；final、Formatter 产物与 State 对应内容一致。
- 同一输入运行 A、B，以及重复运行 B，都产生独立目录；旧文件不被覆盖，Mock 响应队列不会串用。
- 未知流程在调用模型前明确报错；不回退 A。

### 9.3 失败行为

- 覆盖缺字段、错误类型、非对象已解析 JSON，确认原始输入保留且没有模型调用。
- 覆盖 DirectWriter 和 Formatter 各自的模型异常；后续节点不继续生成或格式化。
- 覆盖直接正文详细活动缺失/空白等 Schema 不合格输出，确认不会进入 Formatter 进行隐式补救。
- 覆盖最终稿任务被改写、负阶段时长等既有校验失败，确认无正式 final。
- 对 B 覆盖 final 写入中断、state 写入失败、save trace 一次性写入失败；继承基线清理残留 final 的保证。
- 对新增必要记录写入覆盖至少一个代表性故障，确认没有成功假象或失败运行残留正式 final。
- 失败 State 和 trace 中的 run_id、失败节点、错误与已执行路径一致；未知用量不记成零。

### 9.4 元信息与资料

- 流程标识、版本、Agent 参数、提示词哈希与实际运行对象一致；B 不列入大纲 Agent。
- 输入哈希在既定序列化规则下稳定，内容改变会影响哈希；原始输入与标准化任务哈希不混用。
- Git 可用时取得实际提交和修改状态；不可用时保留未知，不阻断生成或伪造信息。
- 相同固定资料条件下，两条流程记录实际收到的内容；空资料、未执行与失败可区分。
- 能证明 A 的两处检索和 B 的一处检索按既定规则执行，资料记录不是从 final.sources 猜测得到。
- 计时非负、范围有说明；Mock 用量仍为 `null`。
- 若本次代码涉及旧记录读取，验证其容忍新增字段缺失，且不自动把未知值补成成功、零用量或确定流程身份。

### 9.5 工程收尾

- 无网络单元测试及 Mock E2E 通过；使用假客户端的 Provider 测试不调用真实服务。
- 现有数学、生物（文件名为 science）和语文三个输入分别经 A、B 的 CLI Mock 路径成功运行，核对状态、产物与元信息。
- 默认执行不读取 API Key、不隐式加载 `.env`；既有 `--real` 加载边界保持不变。
- 报告实际执行的测试及结果、未执行项目和遗留限制。`runs/` 仍按仓库规则作为本地产物，不承诺其自动进入版本控制。
- 文档描述与实际实现一致，不能把预留接口、真实调用或教学评价标为已完成。
