# 教案生成项目：完整工作流的比较与优先级

日期：2026-09-17

依据：2026-09-17 核对的仓库最新版本 [b9dcded](https://github.com/tpfStone/multi_agent_lesson_planner/commit/b9dcded7e74d6b63e7b4b9c9f78e37ea7378bf02)（本地 `HEAD` 与远端 `main` 一致）。

## 建议先做什么

**保留现有基线，先完成“直接撰写正文”这一条候选。比较时，同一个备课需求分别交给两条完整工作流，各自从输入运行到保存。**不只运行差异片段，也不把基线生成的大纲或正文交给候选流程使用。

优先级根据比较问题是否清楚、实现规模和当前准备条件排序，**不代表预期教学质量高低**。优先完成一条候选，不必把以下所有线路都实现。

## 当前阶段：完整生成工作流

现有基线 A：**输入 → 标准化 → 大纲规划 → 正文撰写 → 格式整理 → 结构校验 → 保存。**

### 1．候选 B：直接撰写——最高优先级，现在做

**输入 → 标准化 → 直接撰写完整正文 → 格式整理 → 结构校验 → 保存。**

- **与 A 比较什么：**面对同一需求，分步规划写作与直接写作这两套完整流程，产物、耗时和失败情况有何差异。
- **推荐理由：**差异明确、改动较小，可复用现有正文结构及后半段处理。
- **解释边界：**主要改变是取消独立大纲步骤，但提示词和调用次数也随之改变。结果反映整套流程的差异，不能直接证明“大纲本身”造成了全部变化。

### 2．候选 C：分阶段撰写后整合——第二优先级

**输入 → 标准化 → 大纲规划 → 分阶段撰写 → 全文整合 → 格式整理 → 结构校验 → 保存。**

- **与 A 比较什么：**整体写作与分工后整合两套流程，是否产生不同结果，以及分工是否增加重复和衔接问题。
- **推荐理由：**更直接探索多 Agent 分工；但需要增加阶段分配、整合步骤，规模大于 B。
- **运行方式：**A、C 各自生成自己的大纲，再完成各自后续步骤。当前主比较不共享模型生成的大纲。

### 3．候选 D：需求分析后撰写——第三优先级，可选

**输入 → 标准化 → 需求分析 → 完整正文撰写 → 格式整理 → 结构校验 → 保存。**

- **与 A 比较什么：**写作前先确定教学安排，还是先梳理显式需求与约束，这两种完整流程有何差异。
- **可选理由：**规模适中，但需求分析容易与标准化或大纲重叠。必须明确独立职责；若只是改名，就没有清楚的比较价值。

## 后续阶段：带反馈修订的完整工作流

以下以基线 A 为例，先固定生成方式，每次只加入一轮修订。它们属于后续研究，不与 B、C、D 同时推进；反馈依据和效果判断方式需由团队与老师明确。

### 4．加入一轮反馈修订——进入修订研究时先做

**输入 → 标准化 → 大纲规划 → 正文撰写 → 反馈 → 修改正文 → 格式整理 → 结构校验 → 保存。**

与不修订的 A 完整运行比较，观察增加反馈与修改后的结果及额外投入。先了解一次修订的作用，再研究更复杂的反馈机制与多轮循环；同时保留每次运行自己的修改前后版本。

### 5．两种反馈组织方式——修订阶段的后续比较

- **先评价再建议：**输入 → 标准化 → 大纲规划 → 正文撰写 → 评价教案 → 分析问题并提出建议 → 修改正文 → 格式整理 → 结构校验 → 保存。
- **先建议再审核：**输入 → 标准化 → 大纲规划 → 正文撰写 → 提出批评与建议 → 审核建议 → 修改正文 → 格式整理 → 结构校验 → 保存。

比较两套反馈机制对整条流程结果的影响。后一条的 Judge 审核的是建议；若它仍在评价教案，就需要重新明确差异。检查字段和结构的 Validator 不承担教学质量评审。

### 6．修订大纲再重写 vs 直接修订正文——较低优先级

- **从大纲修改：**输入 → 标准化 → 大纲规划 → 正文撰写 → 反馈 → 修订大纲 → 重写正文 → 格式整理 → 结构校验 → 保存。
- **从正文修改：**输入 → 标准化 → 大纲规划 → 正文撰写 → 反馈 → 修订正文 → 格式整理 → 结构校验 → 保存。

比较两种修改路径的整体结果和成本。反馈生成规则尽量一致；由于改动范围不同、问题类型尚待明确，放在较后阶段。

## 代码与运行：复用实现，独立执行

**不需要整条重写代码，需要每条完整运行。**以 A、B 为例：新增直接撰写 Agent，输出现有 `LessonDraft`；入口手动选择流程，默认仍走 A。相同的标准化、Formatter、校验和保存代码可以共用，但每次都处理本次运行自己的数据。

同一需求分别启动 A、B，各自建立运行编号和目录，各自执行完整路径。B 没有大纲步骤，就不运行或伪造该步骤。失败时按现有方式停止并保存失败记录，不强行产生成品。补齐 B 的模拟响应与工程测试即可，无须先建通用平台。

为后续比较，至少保留：

- 相同输入的关联信息、独立运行编号、流程名称和版本。
- 实际模型与参数、代码及提示词版本、所用资料。
- 大纲（如有）、格式整理前的正文、最终稿、校验结果和失败记录。
- 耗时、可获得的 token 用量；未知用量保留为未知。

各流程尽量使用相同模型、输入、资料条件和输出结构。Formatter 本身也调用模型，因此保留整理前后结果。先用现有输入完成工程验证和小规模真实试运行；后续通过多个需求、适量重复运行观察差异，不凭一次结果判断优劣。

## 局部对照实验放在哪里

**整条流程比较是主线，局部对照用于后续解释差异。**例如，A、C 的结果不同后，再给两种写作方式同一份大纲，检查差异是否仍然存在；比较修订机制时，也可补充使用同一初稿的实验。

这些实验回答“哪个环节可能造成差异”，应单独标记，不与完整运行结果混在一起。它们不替代当前从输入到保存的完整工作流比较。

## 后续边界

正式教学评价标准由团队与老师确认，不直接采用仓库里的占位评分字段和阈值。工程校验通过或模型自评分上升，都不能单独证明教学质量提高。修订时保留原稿、新版本、来源和反馈；固定流程的一轮修订明确后，再探索多轮修订，每轮自动切换流程放到更后面。
